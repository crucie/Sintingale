# Sintingale v2: ENS Teams, Splits and Agents — Implementation Brief

**Audience:** the engineering agent implementing this work.
**Baseline:** `ref_doc.md` (the existing Sintingale spec: Whitechain settlement, Arkiv ledger, Next.js app, relayer). This brief describes the **delta** on top of that baseline. Where the two conflict, this brief wins.
**Event:** ETHGlobal Mumbai hackathon. Time is the scarcest resource, so build in the tiers defined in section 4 and stop at the tier boundaries if time runs out.

---

## 1. Objective

Extend Sintingale from a plain checkout-and-invoice tool into **billing infrastructure where a company's ENS name is its billing organization**:

- Customers pay a verified merchant name (`acme.eth`), not a raw address.
- Merchants who own an ENS name can invite team members, who receive ENS **subnames** (e.g. `alice.acme.eth`).
- Each **project** has a **revenue-share table** keyed to team members. Payments to a project are split accordingly.
- Merchants can authorize **agents** (automation/AI) via subnames (e.g. `billing-bot.acme.eth`) with **time-boxed, capped permissions**.
- All organizational state (invites, grants, shares, payouts) lives as queryable, expiring entities on Arkiv. Money moves only on Whitechain.

**Pitch line to preserve in the UI copy and README:**
> Sintingale turns a company's ENS name into its billing organization: customers pay `acme.eth`, teammates and agents are subnames, and every split, invite and permission is an expiring, queryable record.

### 1.1 Access rules (product requirements)

| Actor | Requirement |
|---|---|
| **Any signed-up user (customer)** | Can connect a wallet and pay. **No ENS name required.** |
| **Merchant with an ENS name** | Can create an org, invite team members, issue subnames, create projects and define revenue shares, and create agent grants. |
| **Merchant without an ENS name** | Can still create plans/invoices and receive payments (baseline behavior). Team, split and agent features are disabled with a clear "Connect an ENS name to unlock teams" prompt. |
| **Team member** | Holds a subname under the org. Can view the org's projects they belong to and claim their share. Cannot change splits unless role permits. |
| **Agent** | Holds a subname plus an unexpired `grant`. Can perform only the actions and spending caps in the grant. |

### 1.2 Assumption to confirm

"Tickets" in the original request is interpreted as **a share of the revenue generated by each project's payments**. If the product owner meant something else (support tickets, event tickets, invoice assignment), stop and ask before building section 6 (splits). Everything else in this brief is independent of that interpretation.

## 2. Hard constraints and design decisions (do not deviate)

1. **Three networks, strictly separated by responsibility.**
   - **Whitechain Sepolia (chain ID 1874, gas token WBT):** all payments, splits and claims.
   - **Arkiv testnet:** all billing and organizational state entities.
   - **Ethereum Sepolia:** ENS only (name resolution, subname issuance, text records). **Never** put payments on Sepolia. Never require customers to switch to Sepolia.
2. **The Whitechain contract cannot resolve ENS names.** ENS lives on Ethereum. Resolve names to addresses **off-chain at configuration time**, store the resulting **addresses** on-chain, and provide a "re-sync" action to refresh them. The UI must label this honestly ("Share is paid to the address currently resolved for alice.acme.eth").
3. **Do not burn ENS fuses.** ENS recommends waiting for ENSv2 before locking names with fuses, and locked names may be restricted on upgrade. Create subnames with `setSubnodeOwner`/`setSubnodeRecord` using **no fuses** (fuses = 0). The merchant must be able to remove or replace a member's subname. Never describe these subnames as "unruggable" anywhere in UI or docs.
4. **Trust filtering on Arkiv.** Any consumer logic that reads `receipt`, `entitlement`, `payout` or `grant` entities must filter on `$creator == RELAYER_ADDRESS`. Entities created by other addresses must be ignored. `invite` and `project` entities are created by the merchant wallet and validated against the org owner.
5. **Pull payments, not push.** The splitter credits claimable balances. It never loops over members sending tokens in the payment transaction.
6. **Arkiv expiry is a feature, use it:** invites (hours to days), agent grants (hours to days), pending invoices (due date plus grace). Do not build cron jobs for expiry.
7. **No private keys in client code.** The relayer key is server-only.
8. **Verify before you build.** Several external facts are unconfirmed (see section 13). Check them first and report discrepancies.

## 3. Target architecture (delta)

```
Customer wallet ──pay──▶ PaymentRouter ──▶ ProjectSplitter (claimable balances)
   (Whitechain)               │ emits Paid / Credited
                              ▼
 Relayer ── polls logs ──▶ writes receipt, payout, entitlement ──▶ ARKIV
                              ▲
 Merchant dashboard ──creates org, project, invite, grant (signed by merchant wallet)──▶ ARKIV
        │
        └──▶ ENS (Ethereum Sepolia): resolve names, issue subnames, read text records
```

New components:

| Component | Network | Responsibility |
|---|---|---|
| `ProjectSplitter` (extends or sits beside `PaymentRouter`) | Whitechain | Per-project share tables, claimable balances, withdrawals |
| ENS service layer (`lib/ens.ts`) | Sepolia | Resolve names, verify ownership, issue/remove subnames, read/write text records |
| Org / team module | App + Arkiv | Orgs, projects, members, invites |
| Agent grant module | App + Arkiv | Grants, grant verification middleware |
| Relayer additions | Whitechain + Arkiv | Write `payout` entities, enforce grant checks |

### Tier 0: Baseline (assumed done or in progress)
One-time invoice → pay on Whitechain → relayer writes `receipt` on Arkiv → dashboard queries Arkiv. If this is not working end to end, finish it first. Nothing below matters without it.

- Create org and projects.
- Invite members (expiring invites), accept invite, subname issued.

- Issue an agent subname.
- Create expiring `grant` entities with scope and spending cap.
- Grant verification on invoice-creation API calls.

Sponsored gas, entitlement-based access (`hasAccess`), receipt verification page, World ID.

**Cut order if behind schedule:** Tier 4 → Tier 3 → splits automation details (keep the manual claim flow) → team UI polish. **Never cut Tier 1.**

## 6. Tier 2: Teams and revenue splits — detailed tasks

### 6.1 Concepts

- **Org:** one per ENS name. Owned by the wallet that proved ownership.
- **Project:** belongs to an org; has a name, a payout policy and a share table. Invoices and plans reference a `projectId`.
- **Member:** a person with a subname under the org. Has a role and a share in one or more projects.
- **Share:** expressed in **basis points (bps)**. A project's shares must sum to **10,000 bps** exactly. The owner's share is explicit, not implicit.

### 6.2 Subname model

```
acme.eth                         (org owner)
├─ alice.acme.eth                (member)
├─ bob.acme.eth                  (member)
└─ billing-bot.acme.eth          (agent, Tier 3)
```

Flat subnames under the org name are sufficient. Do **not** build per-project nested subnames unless everything else is done. Project membership is recorded in Arkiv, not in the name hierarchy.

### 6.3 Invite and membership flow

1. Owner creates an `invite` entity: `orgId`, `inviteeAddress` (and optional intended label), `role`, `projectShares[]`, with expiry **48 h**.
2. Owner shares an invite link containing the invite entity key.
3. Invitee opens the link, connects a wallet, and the app verifies: invite exists (not expired), `inviteeAddress` matches (if specified), and the label requested is valid and unused.
4. Owner (or an owner-authorized flow) calls NameWrapper `setSubnodeRecord(parentNode, label, owner=invitee, resolver, ttl, fuses=0, expiry)` on Sepolia. Set the address record so the subname resolves to the member's payout wallet.
5. App writes a `member` entity and marks the invite consumed (write a `member` entity, and rely on invite expiry or write an `inviteAccepted` marker, so stale invites cannot be reused).
6. Member appears in the project share editor.

> **Implementation note:** the subname issuance transaction must be signed by the **org owner's** wallet. Step 4 therefore happens in the owner's dashboard ("Approve member" button after the invitee accepts), not in the invitee's session. Do not give the relayer ownership of the org's ENS name.

### 6.4 Smart contract: `ProjectSplitter`

Implement on Whitechain in Solidity (Foundry or Hardhat). Either extend `PaymentRouter` or add a separate contract that `PaymentRouter` calls. Keep the interface below regardless.

```solidity
struct Share { address account; uint16 bps; }   // bps sum must equal 10_000

event ProjectCreated(bytes32 indexed projectId, address indexed owner);
event SharesUpdated(bytes32 indexed projectId, uint256 version);
event Credited(bytes32 indexed projectId, bytes32 indexed invoiceId, address token, uint256 amount, uint256 version);
event Claimed(bytes32 indexed projectId, address indexed account, address token, uint256 amount);

function createProject(bytes32 projectId, Share[] calldata shares) external;          // caller becomes owner
function updateShares(bytes32 projectId, Share[] calldata shares) external;           // owner only; applies to FUTURE payments
function payProjectInvoice(bytes32 projectId, bytes32 invoiceId, address token, uint256 amount) external;
function claim(bytes32 projectId, address token) external;                            // pays msg.sender's accrued balance
function claimable(bytes32 projectId, address account, address token) external view returns (uint256);
```

**Required behavior**

- `payProjectInvoice` pulls `amount` of `token` from the payer into the contract and **credits** each account `amount * bps / 10_000`.
- **Rounding dust** (remainder from integer division) is credited to the project owner. Add a test proving the sum of credits always equals `amount`.
- `invoiceId` can only be paid once (reverts on repeat).
- `updateShares` validates: non-empty, no duplicate accounts, no zero address, `sum(bps) == 10_000`. It increments a `version` counter. Past credits are **never** recalculated.
- `claim` uses checks-effects-interactions, plus a reentrancy guard. Zero balance reverts or no-ops (choose one and test it).
- `token` must be on an allow-list (the configured USDT/MockUSDT) in the MVP.
- No admin ability to move user balances. Document any owner or pauser powers explicitly.
- Contract must support tokens with 6 or 18 decimals. Never hard-code decimals.

**Tests required (Foundry/Hardhat):** exact split with round numbers, split with dust, double-pay revert, bad bps sum revert, duplicate account revert, non-owner `updateShares` revert, claim happy path, claim twice, reentrancy attempt, updating shares does not alter earlier credits.

### 6.5 ENS-to-address snapshot

- When the owner saves a share table in the UI, the app resolves each member's subname to an address (Sepolia), shows the resulting addresses for confirmation, then calls `createProject` / `updateShares` on Whitechain with those addresses.
- Store the mapping `{ subname, address, resolvedAt }` in the project's Arkiv entity so the dashboard can show names while the contract holds addresses.
- Provide a **"Re-sync addresses"** action: re-resolves all names, diffs against the stored addresses, and prompts the owner to submit `updateShares` if any changed.
- Show a warning badge on any member whose current ENS resolution differs from the on-chain address.

### 6.6 Relayer additions

For each `Credited` event:
1. Look up the invoice (Arkiv) by `invoiceId` and confirm `projectId`, `amount` and `token` match the event. On mismatch, log loudly and **do not** write the receipt.
2. Write `receipt` (baseline behavior).
3. Write one `payout` entity per credited account: `projectId`, `invoiceId`, `account`, `subname`, `amount` (numeric), `shareBps` (numeric), `version` (numeric), `txHash`.
4. Be idempotent: check for existing `receipt`/`payout` entities with the same `txHash` and `invoiceId` before writing.

### 6.7 Arkiv entities added in Tier 2

All numeric fields must be stored as **numeric attributes** where range queries are needed.

| `type` | Creator | String attrs | Numeric attrs | Expiry |
|---|---|---|---|---|
| `org` | Merchant wallet | `orgId`, `ensName`, `owner`, `payout` | — | long |
| `project` | Merchant wallet | `orgId`, `projectId`, `name`, `splitContract` | `version` | long |
| `member` | Merchant wallet | `orgId`, `subname`, `address`, `role`, `projectIds` | `joinedAt` | long |
| `invite` | Merchant wallet | `orgId`, `inviteId`, `inviteeAddress`, `role` | `createdAt` | **48 h** |
| `payout` | Relayer | `projectId`, `invoiceId`, `account`, `subname`, `txHash` | `amount`, `shareBps`, `version`, `paidAt` | months |

Payload JSON holds anything not queried (display names, descriptions, the full share table snapshot).

**Authorization rule for reads that drive access control:** `org`, `project`, `member` and `invite` entities are valid only if `$creator` equals the `owner` recorded on the `org` entity (or, for members, the org owner). Implement this as a single shared helper, `isValidOrgEntity()`, and use it everywhere.

### 6.8 API additions

| Method | Route | Purpose | Auth |
|---|---|---|---|
| `POST` | `/api/orgs` | Verify ENS ownership and create the `org` entity | Wallet signature |
| `POST` | `/api/projects` | Create a project (Arkiv entity, then on-chain `createProject` initiated by the client) | Org owner |
| `PUT` | `/api/projects/:id/shares` | Resolve names, return the proposed share table for confirmation | Org owner |
| `POST` | `/api/invites` | Create an invite entity and link | Org owner |
| `GET` | `/api/invites/:key` | Resolve an invite for the invitee | Public |
| `POST` | `/api/invites/:key/accept` | Invitee accepts, owner approval pending | Invitee signature |
| `POST` | `/api/members/:id/issue-subname` | Returns the transaction parameters; the owner's wallet signs and submits | Org owner |
| `GET` | `/api/projects/:id/payouts` | Payout history from Arkiv | Org owner / member |
| `GET` | `/api/me/claimable` | Aggregated claimable balances for the connected wallet | Wallet |

Signed-message auth: use EIP-4361 (Sign-In with Ethereum) or a simple nonce-signature scheme. Reject replays with a nonce store and short expiry.

### 6.9 Acceptance criteria for Tier 2
- [ ] A merchant with ENS creates an org, a project and a 3-way split (for example 50/30/20) and sees the on-chain share table match the UI.
- [ ] An invite expires on its own after the configured time with no cleanup code, and the accept link then shows "This invite has expired."
- [ ] After a customer pays a project invoice, each member's claimable balance equals their exact share, dust included.
- [ ] A member can claim from their own wallet and the balance drops to zero.
- [ ] Changing shares affects only later payments; earlier `payout` entities are unchanged.
- [ ] Merchant without ENS sees locked team features and a working basic checkout.
- [ ] Fake `payout`/`receipt` entities created by a different wallet do **not** appear in any dashboard.

## 7. Tier 3: Agent verification — detailed tasks

### 7.1 Concepts

An **agent** is an automated actor (for example a billing bot or AI assistant) that the merchant authorizes to perform limited actions. Identity = an ENS subname the merchant issued. Permission = an unexpired `grant` entity on Arkiv.

### 7.2 `grant` entity

| Field | Type | Meaning |
|---|---|---|
| `orgId` | string attr | Owning org |
| `agentName` | string attr | e.g. `billing-bot.acme.eth` |
| `agentAddress` | string attr | Resolved address at grant time |
| `scope` | string attr | Comma-separated actions, e.g. `invoice:create` |
| `projectId` | string attr (optional) | Restrict to one project |
| `maxAmount` | numeric attr | Per-invoice cap in token base units |
| `maxTotal` | numeric attr | Cumulative cap within the grant's life |
| `createdAt` | numeric attr | Timestamp |
| expiry | Arkiv expiry | Hours to days. **The grant is dead when the entity expires.** |

### 7.3 Verification middleware

Create `verifyAgentRequest(req)`, used on any agent-callable endpoint (start with `POST /api/invoices`):

1. Parse and verify the request signature, recovering the signer address.
2. Resolve `agentName` on Sepolia and confirm it is a subname of a registered org's ENS name.
3. Confirm the resolved address equals the signer.
4. Query Arkiv for an unexpired `grant` with matching `orgId`, `agentName`, and a `scope` that covers the requested action. Validate `$creator` is the org owner.
5. Enforce `maxAmount`, and `maxTotal` by summing the agent's prior invoices created under this grant.
6. On any failure, return `403` with a machine-readable reason code (`AGENT_NAME_MISMATCH`, `GRANT_EXPIRED`, `SCOPE_DENIED`, `CAP_EXCEEDED`, and so on).
7. Record the agent identity on the created invoice (`createdBy=agentName`) so actions are auditable.

### 7.4 UI
- Agents tab: list agents, active grants with a live expiry countdown, revoke button.
- Revoke = delete the entity if the SDK supports it; otherwise write a `revocation` entity and have the middleware check it.
- Invoice rows created by an agent show a small agent badge.

### 7.5 Acceptance criteria
- [ ] A valid agent creates an invoice within its cap and succeeds.
- [ ] The same agent over its cap is rejected with `CAP_EXCEEDED`.
- [ ] After the grant expires, the same request is rejected with no code change or manual step.
- [ ] A request signed by a different address claiming the same agent name is rejected.
- [ ] An agent with scope for project A cannot create invoices for project B.

## 9. Data layer organization

Keep a single data-access layer so storage choices stay swappable:

```
lib/
├─ arkiv/
│  ├─ client.ts          read-only and wallet client factories
│  ├─ schema.ts          attribute names, zod validators, entity types
│  ├─ queries.ts         query builders (invoices, payouts, members, grants)
│  └─ trust.ts           $creator filters, isValidOrgEntity()
├─ ens/
│  ├─ client.ts          Sepolia client
│  ├─ resolve.ts         forward/reverse, avatar, text records
│  ├─ ownership.ts       owner check for wrapped and unwrapped names
│  └─ subnames.ts        NameWrapper call builders
├─ chain/
│  ├─ whitechain.ts      chain config, contract ABIs and addresses
│  └─ splitter.ts        typed wrappers for ProjectSplitter
└─ auth/
   ├─ siwe.ts            nonce and signature verification
   └─ agent.ts           verifyAgentRequest()
```

No component or route should call Arkiv, ENS or the contracts directly. Everything goes through these modules.

## 14. Known limitations (must be stated in the README and demo)

1. ENS names are resolved off-chain; the Whitechain contract pays **addresses captured at configuration time**. Wallet changes require a re-sync.
2. Subnames are **not locked** (no fuses burned). The org owner can revoke or replace them. This is intentional.
3. The relayer is a single trusted writer for `receipt` and `payout` entities. Receipts can be cross-checked against Whitechain logs, but this is not a trustless bridge.
4. Testnet-only; MockUSDT may be used.
5. Share changes are forward-looking only.

## 15. Things the agent must not do

- Do not put any payment or token transfer on Sepolia.
- Do not burn ENS fuses or describe subnames as permanent or unruggable.
- Do not let the relayer own or control the merchant's ENS name.
- Do not trust Arkiv entities without the `$creator` check.
- Do not loop token transfers to members inside the payment transaction.
- Do not hard-code token decimals, chain IDs or addresses outside configuration.
- Do not add libraries or services not required by this brief without noting why.
- Do not expand scope beyond the current tier to "improve" things. Report ideas instead.
